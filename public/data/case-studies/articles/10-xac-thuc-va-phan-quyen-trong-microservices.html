Authentication (authentication, answering the question of who you are) and decentralization (authorization, answering the question of what you can do) are always indispensable components of every system, but the level of application depends on each stage. If you do everything too tightly from the beginning, it can increase complexity and slow down the company's growth. But if you do it too late, then you may risk being attacked and the risks that come from it. For an e-commerce company like Tiki, that risk is very present with systems related to payment, virtual currency (Tiki Coins), promotional codes (coupons), gift certificates (giftcards) and many other sensitive systems...

Starting from Monolithic

Tiki is originally a monolithic system, usually in such a system there will be a common module that manages authentication and authorization. After logging in, each user will be given a unique Session ID for identification. The client side can save the Session ID as a cookie and include it in every request. The system will then use the sent Session ID to determine the identity of the accessing user, so that the user does not need to re-enter login information next time.

When the Session ID is sent, the server will determine the identity of the user associated with that Session ID, and will check the user's permission to see whether or not to access that task. The session and cookie solution can still be used, but today we have more requirements, such as Hybrid or SPA (Single Page Application) applications that may need to access many different backend systems, so sessions and cookies taken from one server may not be usable on another server.

Microservices difficult problem

In microservices architecture, the system is divided into many subsystems, responsible for different operations and functions. Each of those subsystems also needs to be authenticated and decentralized. If handled in the manner of the Monolithic architecture above, we will encounter the following problems:

  • Each service needs to perform its own authentication and authorization in its own service. Although we can use the same libraries in each service to do that, the cost of maintaining that common library with many different language platforms is too large.
  • Each service should focus on building its own operations. Building additional decentralization logic reduces development speed and increases the complexity of services.
  • Services will typically provide interfaces in the form of RESTful APIs, using the HTTP protocol. HTTP requests will go through many components of the system. The traditional way of using sessions on the server (stateful) will make it difficult to expand the system horizontally.
  • The service will be accessed from many different applications and users, be it a user, a hardware device, a 3rd-party, crontab or another service. Determining identity and authorization in many different contexts is extremely complicated.

Below are some solutions, techniques and approaches that Tiki has applied to this problem.

Identifier

Use JWT

JWT (Json Web Token) is a type of token that uses an open standard to exchange information along with HTTP requests. This information is authenticated and reliably marked based on the signature. JWT has many advantages over session.

  • Stateless, information is not stored on the server.
  • Easy to develop and expand.
  • Better performance because the server reads information right in the request (if session, it needs to be read in storage or database)

RSA encryption for JWT

The signature will be re-encrypted using HMAC or RSA.

  • HMAC: the JWT originator (token issuer) and the JWT receiver (token verifier) use the same secret code for encryption and verification.
  • RSA: uses a key pair, the JWT initializer uses the Private Key for encryption, the JWT receiver uses the Public Key to check.

So with HMAC, both sides must share the secret code with each other, and the JWT recipient can completely create another valid JWT code based on that secret code. As for RSA, the receiver uses the Public Key to check but cannot create a new JWT based on that key. Therefore, encryption using RSA helps secure signatures better when needing to share JWTs with many different objects.

Use Opaque Token when desired for better session control

Opaque Token (also known as stateful token) is a form of token that does not contain information, usually a random string and requires an intermediary service to check and retrieve information. For example:

{
"access_token": "c2hr8Jgp5jBn-TY7E14HRuO37hEK1o_IOfDzbnZEO-o.zwh2f8SPiLKbcMbrD_DSgOTd3FIfQ8ch2bYSFi8NwbY",
"expires_in": 3599,
"token_type": "bearer"
}

Transparent Token (also known as stateless token) is usually in the form of JWT, this token itself contains information and does not need an intermediary service to check. Let's compare these two types of tokens.

OAuth 2

Tokens will be initialized through OAuth 2, which is the most popular authentication method today, through which a service, or a third-party application can represent (delegation) for users to access a user's resource located on a certain service.

OAuth 2 is an open standard, with full documentation and libraries in all different languages, making integration and development based on it easy and fast.

Architecture for authentication and authorization

After having the identifier and protocol used to communicate, the next question is to answer the question of whether the object with that identifier has the right to perform an action, access a certain resource or not. At Tiki, besides newly built services, there still exist old systems (legacy) running in parallel, so currently Tiki has 2 decentralized organization methods as below.

Authentication and decentralization at the edge layer

According to the model, all requests will be authenticated when going through API Gateway or BFF (Backend For Frontend). BFF is the service layer at the edge (Edge Service) designed specifically for each application (eg IOS, Android, Management UI). We will place authentication and authorization at this edge layer

  • API Gateway will require all requests to include a token for identification
  • If this token is JWT (for OpenID Connect), the Gateway can check the validity of the token through signature, claim or issuer.
  • Since this token is Opaque Token, the Gateway can analyze (introspect) the token, exchange it for JWT and pass it on to the services.
  • API Gateway or BFF checks policies to see if they are valid through the central Authorization Server.
  • Microservices do not implement any authentication or authorization layer and can be freely accessed within the internal network.

This model has similarities with the Monolithic architecture when placing decentralized authentication at certain services, construction and maintenance will cost less, but will reveal a huge security gap in the inner layer because the services can freely access each other. We can set some rules from a network perspective for these internal services, but these rules will be relatively simple and cannot meet the mutual data access operations between independent teams/services (by extension, internal companies).

Authentication and authorization at services

In this model, each service (except for some exceptions) is designed and built with extensible APIs (API Interfaces). can serve the outside world. A service today is built for internal operations within the company, but tomorrow may be ready to open to external partners and programmers. This will help services/teams be completely proactive about existing resources, which objects are allocated to those resources, whether they are accessed partially or fully...

To do this, a huge role will lie in the IAM (Identity Access Management) service. IAM holds the identities of all objects (users, services, commands...) along with detailed permission rules for each type of resource.

The fact that each service must perform its own authentication and authorization will increase costs when building services. Outside of the main operations, an additional middleware layer is needed to communicate with IAM. However, services will have complete autonomy, be proactive in providing resources to objects, and accelerate development because in many cases clients can access services directly without needing to develop an additional BFF layer in the middle.

Access Control

Building an effective rule system is never easy, as increased professional requirements lead to more complex decentralization requirements. Let's take a specific example to clarify, each normal application will assign rights to a specific member (for example, John has the right to create products). Expanding into a microservices system, objects here can be users, services, crontabs...

There are several approaches to decentralization as above, try going through different approaches to get different perspectives.

Access Control List (ACL)

In the example above you can see a matrix of objects and permissions, it is roughly equivalent to file management on Linux (chmod) and is suitable for applications with few objects. When the system grows, this model will be unmanageable because the matrix created is too large and complex. Therefore, this model is no longer popular today.

Role-Based Access Control (RBAC)

RBAC links objects to roles, and from roles to permissions. For example role Administratorcan inherit all rights that role Manager yes, this helps reduce the complexity of the permissions matrix, instead of assigning the entire permissions to Administrator then just give Administrator inherit the rights of Manager.

RBAC is very popular and you can see it everywhere. Compared to ACL, RBAC helps reduce complexity when the number of objects + permissions increases. However, RBAC does not satisfy some cases, for example when granting permissions for a product to be edited only by the creator, users in a specific department, or permissions to differentiate between users from many different systems (tenants).

Policy-Based Access Control (PBAC)

PBAC is built on Attribute Based Access Control (ABAC), which defines permissions to express whether a request is allowed or denied. ABAC uses attributes to describe the object that needs to be tested, each attribute is a key-value pair, for example Department = Marketing. Thanks to that, ABAC can help decentralize authority more smoothly, suitable for many different contexts and business rules.

PABC is defined through policies written in a common language XACML (eXtensible Access Control Markup Language). A policy defines 4 objects subject, effect, action and resource. For example john (subject) okay allowed(effect) so that delete(action) product with ID john-leman(resource). At first glance, it is similar to how an ACL is defined

{
"subjects": ["user:john"],
"effect": "allow",
"actions": ["catalog:delete"]
"resources": ["product:john-leman"],
}

We can add subjects, actions as well as resources to the policy if we want.

{
"subjects": ["user:john", "user:katy", "user:perry"],
"effect": "allow",
"actions": ["catalog:delete", "catalog:update", "catalog:publish"]
"resources": ["product:john-leman", "product:john-doe"]
}

You may wonder how PBAC is different from ACL, and here is the difference

Law of priority

  • By default, if there is no appropriate policy, the request will be rejected
  • If there is no policy deny, has at least one policy allow then the request is allowed
  • If there is a policy, deny, then the request is always denied

Regular Expressions

Policies allow declaring the use of regular expressions, as in this example allowing all users to view product information.

{
"subjects": ["user:<.*>"],
"effect": "allow",
"actions": ["catalog:read],
"resources": ["product:<.*>"]
}

Conditions

Policies can add conditions to narrow the scope of rights, for example only applying to a certain IP range, or only allowing the product creator to edit that product.

{
"subjects": ["user:ken"],
"actions" : ["catalog:delete", "catalog:create", "catalog:update"],
"effect": "allow",
"resources": ["products:<.*>"],
"conditions": {
"IpAddress": {
"addresses": [
"192.168.0.0/16"
]
}
}
}
